# 极值追踪系统说明文档

## 📊 系统概述

极值追踪系统用于在市场出现极值信号时，自动记录27个币种的快照，并追踪未来1小时、3小时、6小时、12小时、24小时的价格变化情况。

---

## 🎯 触发条件

系统在以下四种情况下会自动创建快照（带4小时冷却期）：

### 1. 逃顶信号2h极值预警
- **条件**: 每日2h逃顶信号数的最大值 > 50
- **数据来源**: `/api/escape-signal-stats` 中的 `has_2h_peak` 标记
- **说明**: 当2小时窗口内的逃顶信号数量达到历史极值时触发
- **冷却期**: 触发后4小时内不再重复触发

### 2. 27币涨跌幅极值
- **条件**: 
  - 超过100%: 所有27个币种的涨跌幅总和 > 100%
  - 低于-80%: 所有27个币种的涨跌幅总和 < -80%
- **数据来源**: `/api/okx-day-change/latest` 
- **说明**: 市场整体涨跌幅异常极端时触发
- **冷却期**: 上涨和下跌分别独立计算，各有4小时冷却期

### 3. 逃顶信号24h极值
- **条件**: 48小时窗口内的24h逃顶信号最大值 > 200
- **数据来源**: `/api/escape-signal-stats` 中的 `has_24h_peak` 标记
- **说明**: 当24小时逃顶信号数量达到极值时触发
- **冷却期**: 触发后4小时内不再重复触发

### 4. 1小时爆仓金额极值 🆕
- **条件**: 1小时爆仓金额 > 3000万美元（30,000,000 USD）
- **数据来源**: `/api/panic/latest` 中的 `hour_1_amount`
- **说明**: 市场出现大规模爆仓时触发
- **冷却期**: 触发后4小时内不再重复触发

### ⏰ 冷却期机制
- **目的**: 避免同一极值事件的重复触发
- **时长**: 4小时（14400秒）
- **范围**: 每种触发类型独立计算
- **存储**: 冷却期状态保存在 `trigger_cooldown.jsonl`
- **说明**: 不同类型的极值可以同时触发

## 📸 快照内容

每次触发时，系统会记录以下信息：

### 基础信息
- **快照ID**: `EXT_<timestamp>` 格式
- **触发时间**: Unix时间戳 + 北京时间字符串
- **触发类型**: 标记触发的具体条件（可能多个同时触发）

### 27个币的快照
```json
{
  "symbol": "BTC",
  "name": "Bitcoin",
  "price": 45678.90,
  "day_change": 1234.56,
  "day_change_percent": 2.78,
  "volume_24h": 12345678900,
  "market_cap": 876543210000
}
```

### 逃顶信号快照
- 2h信号数量
- 24h信号数量
- 是否处于2h极值
- 是否处于24h极值
- 极值具体数值

### 1小时爆仓快照 🆕
- 1小时爆仓金额（万美元）
- 1小时爆仓金额（美元）
- 24小时爆仓金额
- 恐慌清洗指数
- 时间戳

### 价格追踪记录
记录未来5个时间点的价格变化：
- **1小时后** (1h)
- **3小时后** (3h)
- **6小时后** (6h)
- **12小时后** (12h)
- **24小时后** (24h)

每个追踪点包含：
```json
{
  "timestamp": 1234567890,
  "datetime": "2026-01-18 23:00:00",
  "period": "1h",
  "total_change": 15.67,
  "coins": [
    {
      "symbol": "BTC",
      "name": "Bitcoin",
      "original_price": 45678.90,
      "current_price": 46789.12,
      "price_change_percent": 2.43,
      "original_day_change": 2.78,
      "current_day_change": 3.21
    }
  ]
}
```

## 🗂️ 数据存储

### 文件位置
```
/home/user/webapp/data/extreme_tracking/
├── extreme_snapshots.jsonl    # 快照数据（每行一个JSON对象）
├── trigger_cooldown.jsonl      # 冷却期状态记录 🆕
└── extreme_tracking.jsonl      # 追踪日志（可选）
```

### 快照状态
- **active**: 追踪中（还有未完成的追踪点）
- **completed**: 已完成（所有5个追踪点都已记录）

## 🔧 系统组件

### 1. 核心追踪器
**文件**: `source_code/extreme_value_tracker.py`

主要功能：
- 每10分钟检查一次是否满足极值条件
- 创建快照并保存到JSONL文件
- 定期更新活跃快照的追踪数据
- 当所有追踪点完成后，标记快照为completed

运行模式：
```bash
# 单次运行
python3 source_code/extreme_value_tracker.py --once

# 持续运行（每10分钟）
python3 source_code/extreme_value_tracker.py 10

# 持续运行（自定义间隔，单位分钟）
python3 source_code/extreme_value_tracker.py 5
```

### 2. PM2配置
**文件**: `ecosystem.extreme_tracker.config.js`

```javascript
{
  name: 'extreme-value-tracker',
  script: 'source_code/extreme_value_tracker.py',
  interpreter: 'python3',
  args: '10',  // 每10分钟检查一次
  autorestart: true,
  max_memory_restart: '300M'
}
```

PM2管理命令：
```bash
# 启动
pm2 start ecosystem.extreme_tracker.config.js

# 查看日志
pm2 logs extreme-value-tracker

# 重启
pm2 restart extreme-value-tracker

# 停止
pm2 stop extreme-value-tracker
```

### 3. API接口

#### 获取快照列表
```
GET /api/extreme-tracking/snapshots

参数:
  - limit (int, 可选): 返回数量限制
  - status (string, 可选): active/completed 过滤状态

响应:
{
  "success": true,
  "data": [快照数组],
  "count": 10
}
```

#### 获取单个快照详情
```
GET /api/extreme-tracking/snapshot/<snapshot_id>

响应:
{
  "success": true,
  "data": {快照对象}
}
```

#### 获取统计信息
```
GET /api/extreme-tracking/stats

响应:
{
  "success": true,
  "stats": {
    "total_snapshots": 15,
    "active_snapshots": 3,
    "completed_snapshots": 12,
    "trigger_types": {
      "2h_peak": 5,
      "27coins_high": 8,
      "24h_peak": 2
    },
    "average_price_changes": {
      "1h": 2.34,
      "3h": 4.56,
      "6h": 7.89,
      "12h": 11.23,
      "24h": 15.67
    }
  }
}
```

- 分析极值事件发生时的市场特征

- 在极值出现时参考历史数据制定策略

### 3. 风险管理
- 识别市场异常波动
- 预警潜在的剧烈行情
- 评估持仓风险

## ⚠️ 注意事项

1. **数据依赖**
   - 需要逃顶信号API正常运行
   - 需要27币涨跌数据正常更新
   - 确保数据源API可访问

2. **存储空间**
   - 每个快照约5-10KB
   - 建议定期归档历史数据
   - 预留至少100MB空间

3. **时间同步**
   - 追踪时间基于快照触发时间
   - 时间精度为分钟级别
   - 注意服务器时区设置

4. **API限流**
   - 每10分钟检查一次，不会造成压力
   - API调用失败会自动重试
   - 保持合理的检查频率
